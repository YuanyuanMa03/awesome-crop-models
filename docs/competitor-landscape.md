# Existing lists, model directories, and automation references

Checked on **2026-10-22 (Asia/Singapore)** using public repository APIs, default-branch source trees, README files, license files, and commit history. This is a dated investigation, not an exhaustive proof that no other competing project exists. Star counts are snapshots and do not measure scientific validity.

## Recommendation

**Awesome Crop Models** (`awesome-crop-models`) is a clear, searchable name for a specialist list. A closely named crop-model Awesome list already exists, so the project should acknowledge that prior work and distinguish itself through documented discovery, broad inclusion, transparent screening, and reproducible updates. A hyphenated name alone is not differentiation. [Existing specialist list](https://github.com/EDSEL-skoltech/awesome_crop_models)

The intended position is complementary to **Awesome Agriculture**, the larger general-purpose agriculture list selected as the presentation reference: a readable front page for people, backed by a structured, continuously maintained crop-model repository catalogue. Its subject breadth and current **1,911 stars** make it a relevant discoverability reference; neither fact establishes exhaustive coverage. [Awesome Agriculture](https://github.com/brycejohnston/awesome-agriculture), [metadata snapshot endpoint](https://api.github.com/repos/brycejohnston/awesome-agriculture)

## What to learn from Awesome Agriculture

Its presentation is deliberately simple: an immediately recognizable name, an Awesome badge, a short scope statement, a contents list, topic headings, and compact entries with direct links. Categories span automation, weather, crop-related tools, data, interoperability, farm management, GIS, hardware, machine learning, and remote sensing. The current crop modeling/phenotyping/pathology section is small, while relevant model components also appear under weather. The inference is that a deeper specialist crop-model list can complement it without reproducing its entire agricultural scope. [README](https://github.com/brycejohnston/awesome-agriculture/blob/master/README.md)

It welcomes community contributions and links a contribution guide. A specialist project can adopt the same low-friction pattern: a small repository entry, an understandable inclusion rule, and an issue/PR path. Continuous collection should support that front page; a long raw search-result dump would serve a different reading need. [Contribution guide](https://github.com/brycejohnston/awesome-agriculture/blob/master/contributing.md)

These are observed design features and a project-design inference. This investigation does **not** establish what caused the reference project's popularity, the number of active users, or whether a similar name will produce similar adoption.

## Automation: useful precedents and their limits

[Best-of Generator](https://github.com/best-of-lists/best-of-generator) generates Markdown and refreshes metrics for projects already listed in YAML. It supports scheduled updates through a companion Action. That is automatic metadata maintenance, not a demonstrated automatic search for every new crop-model repository. Its default star/rank/license filters can hide small projects; these defaults conflict with a discovery catalogue intended to retain obscure scientific and historical models. [Generator documentation](https://github.com/best-of-lists/best-of-generator/blob/main/README.md)

There is a licensing discrepancy to resolve before reusing its implementation: the README footer says MIT, but the current LICENSE file and API report GPL-3.0. This report records that conflict and does not select the more convenient interpretation. [LICENSE](https://github.com/best-of-lists/best-of-generator/blob/main/LICENSE), [metadata](https://api.github.com/repos/best-of-lists/best-of-generator)

[Best-of Robot Simulators](https://github.com/knmcguire/best-of-robot-simulators) is a concrete example of this maintenance pattern. Its checked workflow schedules weekly generation, creates an update branch, opens a PR, and prepares a draft release. Its latest default-branch commit is a generated list update dated **2026-10-21**. The workflow explicitly leaves final merging and release publication to a person; it is not evidence of a permanently ownerless system. The repository metadata reports CC-BY-SA-4.0. Current workflow-run success was not verified: the connected GitHub tool rejected the workflow-file runs endpoint used in this check. [Workflow source](https://github.com/knmcguire/best-of-robot-simulators/blob/main/.github/workflows/update-best-of-list.yml), [commit history](https://github.com/knmcguire/best-of-robot-simulators/commits/main/), [metadata](https://api.github.com/repos/knmcguire/best-of-robot-simulators)

GitHub documents that public-repository scheduled workflows can be disabled after 60 days without repository activity, and schedules are disabled by default in forks. A scheduled Action alone cannot substantiate a promise of never stopping. Continued operation needs visible health records, a documented recovery path, and maintainers or an independently operated scheduler. [GitHub workflow documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)

## Proposed differentiation

The following are recommendations, not claims about already implemented features:

1. Keep an Awesome-style front page of verified, useful model projects, and expose the larger discovery catalogue separately as structured data.
2. Discover broadly through multilingual queries, model-family aliases, official organizations, citations, references in existing lists, and related repositories. Record which path found each candidate.
3. Keep repositories, model families, implementations, wrappers, forks, and scientific components as separate identities. Display fork relationships instead of inflating coverage with duplicate forks.
4. Retain low-star, archived, and license-unclear candidates with explicit statuses. A public GitHub repository is not automatically confirmed open source.
5. Refresh repository existence, canonical URL, archive/fork status, license evidence, and latest **commit** date; do not label GitHub `updated_at` as a content-update date.
6. Publish the query plan, checked date, failures, incomplete pages, new-candidate counts, and review state. State coverage as measured search coverage, not a claim that all GitHub repositories have been found.
7. Make the pipeline reusable and transferable: code, configuration, schema, tests, health status, and recovery instructions belong in the public project. Keep repository discovery independent of any future benchmark construction.

This design borrows the readable community surface of Awesome Agriculture and the repeatable generation pattern of Best-of, while adding crop-model-specific discovery and provenance. It does not require copying third-party README descriptions or importing private research material.
